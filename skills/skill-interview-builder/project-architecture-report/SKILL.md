# Project Architecture Report

## Name
`project-architecture-report`

## Description
分析项目代码、配置和文档，生成一份包含整体架构（模块划分、层次关系、技术栈）和核心业务流程（关键路径、数据流向）的 Markdown 报告。当用户说"帮我详细分析一下这个项目，总结出一个架构、流程的报告或文档"时触发。自动扫描项目文件并用 Python 脚本辅助提取模块/函数调用关系和代码依赖层级。

---

## Goal
生成一份可直接存档或分享的 Markdown 报告，包含：
- 项目简介和背景
- 整体架构图（Mermaid）
- 模块划分和职责说明
- 核心业务流程描述
- 关键设计决策和潜在问题

## When to use
当用户提出以下类型的需求时触发：
- "帮我详细分析一下这个项目，总结出一个架构、流程的报告或文档"
- "出份这个项目的架构分析报告"
- "梳理一下项目的模块和流程"
- "分析项目结构，给我一份架构文档"
- 用户明确要求生成项目架构或流程分析的报告

## Do not use
- 用户仅要求修改代码或修复 Bug，不涉及架构分析
- 用户仅要求解释某段代码的功能，不要求整体报告
- 用户要求生成的不是报告/文档（如要求写代码、部署等）
- 当前工作目录不是项目根目录且没有明确的项目路径

## Inputs to collect
运行前自动收集以下信息（无需用户输入）：
1. **项目代码文件**：扫描项目目录下的所有源代码文件（.py, .js, .ts, .java, .go, .rs, .c, .cpp 等）
2. **项目配置文件**：package.json, pyproject.toml, pom.xml, Cargo.toml, go.mod, requirements.txt, Dockerfile, docker-compose.yml 等
3. **项目文档文件**：README.md, CONTRIBUTING.md, CHANGELOG.md, docs/ 目录下的文档等
4. **目录结构**：`find . -type f | head -200` 或 `tree` 命令获取项目目录结构

## Procedure

### Step 1: 了解项目全貌
1. 运行 `tree /F`（Windows）或 `find . -type f` 获取项目目录结构，了解项目规模和文件组织方式。
2. 读取项目根目录下的 README.md 和主要配置文件，获取项目简介、技术栈和依赖信息。
3. 如果存在 `pyproject.toml`、`package.json`、`pom.xml` 等配置文件，提取项目名称、版本、依赖和构建信息。

### Step 2: 运行 Python 脚本分析代码结构
1. 将 `scripts/code_analyzer.py` 脚本复制到项目根目录。
2. 在项目根目录执行：`python code_analyzer.py`
3. 读取脚本输出的 JSON 结果文件（`project_structure.json`），获取：
   - 模块/文件列表及其依赖关系
   - 函数/类定义及其调用关系
   - 模块间的引用和依赖层级
4. 删除临时脚本文件和输出文件。

### Step 3: 分析架构层次
1. 根据 Step 2 的结果，识别项目的核心模块和分层结构：
   - 确定项目的架构模式（如 MVC、分层架构、微服务、单体等）
   - 列出每个模块的职责和边界
   - 分析模块间的依赖关系（哪些模块是核心依赖，哪些是叶子模块）
2. 确定技术栈清单：编程语言、框架、数据库、中间件、第三方服务等。

### Step 4: 梳理业务流程
1. 识别项目的核心业务流程（如用户注册登录流程、数据流转路径、API 调用链等）。
2. 每条流程用文字描述其关键路径和决策点。
3. 标注数据流向（从输入到输出经过哪些模块）。

### Step 5: 识别关键设计决策和潜在问题
1. 从代码和配置中推断设计决策的迹象（如选择了某个特定的框架、数据库、架构模式等）。
2. 标注**已确认的设计决策**（从配置文件和文档中明确看到的），**不要过度推测未经证实的设计意图**。
3. 识别潜在问题区域：
   - 循环依赖
   - 过大的模块（单一职责原则违反）
   - 缺少测试覆盖的模块
   - 已废弃或不再维护的依赖

### Step 6: 生成报告
1. 按照以下模板生成 Markdown 报告，文件名格式：`{project-name}-architecture-report.md`
2. 报告结构：

```markdown
# {项目名称} 架构分析报告

## 1. 项目简介和背景
{基于 README 和配置文件的项目概述}

## 2. 整体架构图
```mermaid
graph TD
    {Mermaid 架构图，展示模块及其依赖关系}
```

## 3. 技术栈
| 类别 | 技术 | 版本 |
|------|------|------|
| 编程语言 | ... | ... |
| 框架 | ... | ... |
| 数据库 | ... | ... |

## 4. 模块划分和职责
### 4.1 {模块A}
- **职责**：{此模块负责什么}
- **关键文件**：{文件路径列表}
- **依赖**：{依赖的模块}
- **被依赖**：{被哪些模块依赖}

## Output format
- **格式**：Markdown 文件（.md）
- **文件名**：`{项目名称}-architecture-report.md`
- **存放位置**：项目根目录
- **编码**：UTF-8

## Definition of done
以下是每条可打勾验证的完成标准：

- [ ] 报告包含**项目简介和背景**（基于 README 和配置文件提取）
- [ ] 报告包含**Mermaid 架构图**，展示模块间的关系和依赖
- [ ] 报告包含**模块划分和职责说明**，列出每个模块的职责和依赖关系
- [ ] 报告包含**核心业务流程**描述（至少 1 条关键路径）
- [ ] 报告包含**技术栈清单**（编程语言、框架、数据库等）
- [ ] 报告指出了**关键设计决策和潜在问题**（基于已确认的信息，不推测）
- [ ] Python 脚本已执行并成功生成代码结构分析结果
- [ ] 报告格式规范（Markdown 语法正确，标题层级合理，可读性良好）

## Failure handling
| 失败场景 | 处理方式 |
|---------|---------|
| 项目目录为空或没有代码文件 | 报告此情况，建议用户切换到有效项目目录后重试 |
| Python 脚本执行失败 | 回退到手动分析：使用 grep/find/bash 命令逐文件分析结构 |
| 没有 README 或配置文件 | 基于代码文件分析结果推断项目信息，并在报告中标注"基于代码推断" |
| 项目文件过多（>1000 个） | 重点分析 src/ 和核心模块目录，忽略 node_modules/.git/__pycache__/ 等 |
| 项目不是有效代码项目 | 提示用户目标目录不是代码项目，建议指定正确的项目路径 |
| Mermaid 图过于复杂（>50 个节点） | 拆分为多张子图，按模块分组展示 |
