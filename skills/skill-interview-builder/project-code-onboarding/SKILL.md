# 项目代码接手引导

## Name
project-code-onboarding

## Description
当用户说"想详细了解某个项目的代码逻辑，好接手项目""帮我分析这个项目的代码结构"或类似表达时，触发本Skill。本Skill会全面探索项目目录，自动生成一份**Markdown格式**的代码接手引导文档，包含架构图、流程图、模块分析、数据流追踪等完整内容，帮助新开发者快速上手。**本Skill只分析理解代码，绝不修改任何代码文件。**

## Goal
生成一份清晰、完整、新人可快速上手的项目代码接手引导文档（Markdown格式），包含流程图和架构图，让新接手项目的开发者无需阅读全部源码即可理解项目全貌。

## When to use
- 用户说"我想详细了解这个项目的代码逻辑，好接手项目"
- 用户说"帮我分析一下这个项目的代码结构"
- 用户说"给我梳理一下这个项目的架构"
- 用户说"这个项目我不熟，帮我看看怎么上手"
- 用户说"新接手一个项目，帮我做个文档"

## Do not use
- 用户要求修改或编辑代码文件时
- 用户要求对代码质量做主观评价时（如"这段代码写得怎么样"）
- 用户只问单个函数或单行代码的含义时（应使用常规代码解释）
- 项目目录为空或非代码项目时

## Inputs to collect
1. **项目路径**：用户指定的项目根目录路径（或自动识别当前工作目录）
2. **项目语言/框架**：通过 package.json / pom.xml / go.mod / requirements.txt 等文件自动识别
3. **项目规模**：通过目录结构和文件数量判断项目大小
4. **用户角色**：确认用户是前端/后端/全栈/DevOps，以调整输出侧重点
5. **用户已有了解**：询问用户是否已了解项目的基本用途和业务背景

## Procedure

### Step 1: 确认项目信息和用户背景
1. 1.1 确认项目根目录路径
2. 1.2 询问用户：这个项目是做什么的？（业务背景）
3. 1.3 询问用户：你是前端/后端/全栈/DevOps？对项目已有多少了解？
4. 1.4 询问用户：有没有特别关心的模块或功能点？

### Step 2: 探索项目概况
1. 2.1 使用 `ls -la` 或 `dir` 查看项目根目录，列出所有文件和文件夹
2. 2.2 读取根目录下的关键配置文件：
   - 语言相关：`package.json` / `pom.xml` / `go.mod` / `Cargo.toml` / `requirements.txt` / `Gemfile` / `build.gradle` 等
   - 项目描述：`README.md` / `CONTRIBUTING.md` / `CHANGELOG.md`
   - 容器配置：`Dockerfile` / `docker-compose.yml`
   - 环境配置：`.env.example` / `.env`（注意不要暴露敏感信息）
3. 2.3 使用 `tree` 或递归遍历获取项目目录结构树（跳过 `node_modules`、`.git`、`dist`、`build`、`__pycache__` 等无关目录）
4. 2.4 生成项目目录结构概览（Markdown 代码块格式）

### Step 3: 生成架构总览图（Mermaid）
1. 3.1 根据项目结构和配置文件，识别项目架构模式（MVC、微服务、单体、前后端分离等）
2. 3.2 绘制 Mermaid 架构图，展示：
   - 主要模块/服务
   - 模块之间的依赖关系
   - 外部依赖（数据库、缓存、消息队列、第三方API等）
3. 3.3 将架构图嵌入文档

### Step 4: 分析核心模块
1. 4.1 识别项目中的核心模块（源码目录的子目录，如 `src/`、`app/`、`lib/`、`services/` 等）
2. 4.2 对每个核心模块，执行以下操作：
   - 读取模块目录下的文件列表，识别入口文件
   - 读取入口文件和关键文件，提取：
     - 模块职责（通过类名、函数名、注释推断）
     - 对外暴露的接口（API端点、导出函数、公共方法）
     - 内部关键逻辑（重要函数/方法的流程）
     - 依赖的其他模块或服务
   - 记录模块的输入和输出
3. 4.3 为每个模块生成 Mermaid 子图（展示模块内部结构）或类图（展示模块关键类/函数关系）

### Step 5: 追踪数据流
1. 5.1 识别核心数据流路径：
   - 用户请求入口 → 控制器 → 服务层 → 数据层 → 响应
   - 或：数据输入 → 处理流程 → 数据输出
2. 5.2 绘制 Mermaid 流程图，展示：
   - 请求/数据从入口到最终响应的完整路径
   - 沿途经过的每个模块和关键函数
   - 决策分支（条件判断、错误处理）
3. 5.3 标注关键数据结构和数据格式转换点

### Step 6: 梳理关键依赖和配置
1. 6.1 读取 `package.json` / `pom.xml` / `go.mod` 等，列出主要依赖库及其用途
2. 6.2 读取 `Dockerfile` / `docker-compose.yml`，梳理部署依赖
3. 6.3 读取 `.env.example` 或配置文件，列出所需环境变量和配置项（**注意去除敏感值**）
4. 6.4 整理数据库 Schema（如果存在 `schema.sql`、`prisma/`、`migrations/` 等目录）

### Step 7: 分析数据库/数据模型（如适用）
1. 7.1 查找数据库定义文件（ORM模型、迁移文件、SQL文件）
2. 7.2 提取实体关系（ER关系）
3. 7.3 绘制 Mermaid ER 图
4. 7.4 标注核心数据表及字段说明

### Step 8: 梳理测试策略
1. 8.1 查找测试目录（`test/`、`tests/`、`__tests__/`、`spec/`）
2. 8.2 列出测试文件数量、测试框架（Jest、pytest、JUnit、Go test 等）
3. 8.3 检查测试覆盖率配置
4. 8.4 总结测试覆盖情况和测试策略

### Step 9: 整理启动和部署方式
1. 9.1 根据 `Dockerfile`、`docker-compose.yml`、`Makefile`、`package.json` 中的 scripts 等，整理启动步骤
2. 9.2 列出开发环境搭建步骤
3. 9.3 列出生产环境部署步骤

### Step 10: 生成最终文档
1. 10.1 将所有内容整合为一份完整的 Markdown 文档
2. 10.2 文档结构如下：

```markdown
# 项目名称 - 接手引导文档

## 1. 项目概述
- 业务背景
- 技术栈
- 项目规模

## 2. 目录结构
- 完整目录树
- 各目录用途说明

## 3. 系统架构图
[Mermaid 架构图]

## 4. 核心模块详解
### 4.1 模块A
- 职责说明
- 内部结构图 [Mermaid 子图]
- 关键文件说明
- 输入/输出
- 核心逻辑

### 4.2 模块B
...

## 5. 核心数据流
[数据流 Mermaid 流程图]

## 6. 关键依赖
- 第三方库及用途
- 部署依赖
- 环境变量配置

## 7. 数据库设计
[ER 图]
- 核心表及字段说明

## 8. 测试策略
- 测试框架
- 覆盖率
- 如何运行测试

## 9. 开发环境搭建
- 前置条件
- 启动步骤
- 常用命令

## 10. 部署方式
- 生产环境部署步骤
- 部署架构图（如适用）
```

3. 10.3 最后将文档输出给用户，并询问：
   - "文档是否完整？有没有遗漏的内容？"
   - "是否需要针对某个模块做更深入的分析？"

## Output format
一份完整的 **Markdown 文档**，包含：
- 清晰的章节结构
- 至少 2 张 Mermaid 图（架构图 + 流程图，根据需要可增加 ER 图、子图等）
- 所有分析结果以结构化文本呈现
- 文档总长度视项目规模而定，但确保新人可读

## Definition of done
- [ ] 项目目录结构已完整列出并标注各目录用途
- [ ] 已生成至少一张架构图（Mermaid），展示模块间关系和外部依赖
- [ ] 已生成至少一张数据流图（Mermaid），展示核心请求/数据的完整路径
- [ ] 每个核心模块的职责、输入输出、关键逻辑已说明
- [ ] 关键依赖（第三方库、服务、环境变量）已完整列出
- [ ] 数据库设计（如适用）已梳理并附 ER 图
- [ ] 测试策略已总结
- [ ] 开发环境搭建和部署步骤已整理
- [ ] 文档中未包含任何敏感信息（密钥、Token、密码等）
- [ ] 用户确认文档完整、无遗漏

## Failure handling
- **项目目录无法访问**：提示用户检查路径是否正确，或确认是否有读取权限
- **项目过大**：如果文件数量超过 5000 或目录层级过深，提示用户指定核心模块范围，分批次分析
- **无配置文件**：通知用户未能识别技术栈，将基于文件扩展名进行推断
- **无 README**：跳过业务背景说明，直接基于代码分析
- **用户不确定关注点**：按默认流程输出完整文档，覆盖所有模块
- **权限不足**：提示用户检查文件权限，跳过无法读取的文件

## Additional resources
本Skill不依赖外部配套文件，运行时自动探索项目目录。
