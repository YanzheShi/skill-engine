## Stage 2: 代码讲解者输出

**📖 代码讲解者：**

### 1. 一句话概括
这个模块用 Redis SET NX EX 实现分布式互斥锁，配合后台 goroutine 做锁续期，确保秒杀场景下库存扣减的原子性。

### 2. 核心抽象

| 结构体/函数 | 职责 |
|---|---|
| `OrderLock` | 锁实例，持有 Redis 客户端、key、token、过期时间 |
| `Acquire()` | 用 SET NX EX 抢占锁，返回是否成功 |
| `Release()` | 用 Lua 脚本校验 token 后删除，防误删他人锁 |
| `watchdog()` | 后台 goroutine，每 3 秒用 PEXPIRE 续期 |

### 3. 关键逻辑路径

```
Acquire:
  1. 生成 UUID 作为 token
  2. SET lock_key token NX EX 10
  3. 成功 → 启动 watchdog goroutine → 返回 true
  4. 失败 → 返回 false

Watchdog:
  每 3 秒 → PEXPIRE lock_key 10000（仅当 token 匹配）

Release:
  1. 停止 watchdog
  2. Lua: if GET lock_key == token then DEL lock_key
```

### 4. 隐含假设 & 面试热点

- **假设 1**：Redis 单点写入成功即认为锁生效（未开启 Redlock）
- **假设 2**：业务处理时间 << 锁超时时间（100ms << 10s）
- 🔥 **热点 1**：Redis 主从切换导致锁丢失（你提到的第 2 个困惑）
- 🔥 **热点 2**：Watchdog 续期失败的处理（Redis 抖动时）
- 🔥 **热点 3**：为什么用 Lua 脚本释放锁

### 5. 待澄清
- 是否使用了 Redis Cluster？还是单实例？
- 锁竞争失败时是否有排队/重试机制？

---

**Human 回答：**

> 目前是 Redis 主从架构。丢锁的场景是：
> 1. 客户端 A 在 master 上 SET NX 成功拿到锁
> 2. master 还没把 SET 同步到 slave 就挂了
> 3. slave 被提升为新的 master
> 4. 客户端 B 在新 master 上 SET NX 也成功 → 两个客户端同时持有锁
> 
> 解决方案可以用 Redlock（多节点投票），或者接受这个风险用兜底措施。

---

**🔍 面试官 追问 #2：**

### 本轮追问
> 你说"用兜底措施"，具体是什么？如果不用 Redlock，你的兜底方案是什么？这个方案的覆盖率有多少？

### 追问动机
从"知道问题"推进到"能落地解决"，考察工程实战能力。

---

**Human 回答：**

> 兜底是在库存扣减时加一个**数据库唯一约束**（商品ID+订单状态），即使锁丢了，最终写入数据库时也会因为唯一键冲突而失败。
> 
> 覆盖率：能防止超卖，但不能防止"两个请求都通过了库存校验但只有一个成功"带来的用户体验问题（一人看到成功一人看到失败）。
> 
> 另外加了监控：如果检测到锁持有时间异常长，触发告警。

**🔍 面试官 追问 #3：**

### 本轮追问
> 你的 watchdog 每 3 秒续期。如果 Redis 在续期的那一瞬间超时（网络分区），你的代码会怎么表现？会不会出现"锁已过期但 watchdog 还在跑"的僵尸状态？

### 追问动机
考察对**边界条件与失败模式**的思考深度。

---

**Human 回答：**

> 会的。如果 Redis 网络分区超过 10 秒，锁会过期，但 watchdog 还在跑（因为它每 3 秒重试 PEXPIRE，网络恢复后可能又续上）。
> 
> 这会导致"锁已过期 → 其他客户端拿到了锁 → 原客户端网络恢复后 watchdog 又续上了"的竞态。
> 
> 改进方案：watchdog 续期时检查 Redis 返回的剩余 TTL，如果 < 0 说明锁已丢失，主动退出并触发告警。

## Stage 5: 架构评审 + 收敛沉淀

**🏛️ 架构评审员：**

### ✅ 合理之处
1. **Redis 锁 + DB 唯一约束双重保险**：在秒杀场景下是务实的选择，比纯 Redlock 简单且够用
2. **Lua 脚本释放锁**：避免了"误删他人锁"的经典 bug

### ⚠️ 风险之处

| 风险点 | 严重度 | 触发条件 | 潜在后果 |
|---|---|---|---|
| Redis 主从切换锁丢失 | 🟡中 | Redis master 宕机 | 极低概率超卖（有 DB 兜底） |
| Watchdog 僵尸续期 | 🟡中 | 网络分区 > 10s | 锁语义失效 |
| 锁粒度过粗 | 🟢低 | 热门商品集中 | 吞吐量受限 |

### 🚀 演进方向

**方向 A：引入 Redlock（彻底）**
- 做法：部署 5 节点 Redis Cluster，多数派投票获取锁
- 收益：消除主从切换锁丢失问题
- 代价：延迟翻倍、运维复杂度高、Martin Kleppmann 的批评仍需注意
- 适用时机：当超卖损失 > Redlock 运维成本时

**方向 B：分段锁 + 本地队列（改良）**
- 做法：按商品 ID hash 到 N 个本地队列，单线程消费
- 收益：彻底避免分布式锁，吞吐量提升 10x
- 代价：需要改造架构，引入消息队列
- 适用时机：秒杀规模继续增长 5 倍以上时

### 💡 一句话总结
当前方案是"够用且务实"的，最大短板不是锁本身，而是**缺乏锁失效的自动检测与优雅降级**。

### 2. 必须补充的边界用例（Top 5）

#### 用例 1：Redis 连接超时
- **场景**：Redis 在 SET NX 时网络超时
- **输入**：模拟 Redis dial timeout
- **预期**：Acquire 返回 false，不 panic，不泄漏连接
- **为什么重要**：当前代码没有处理 context deadline，可能 goroutine 泄漏

#### 用例 2：锁过期后被他人抢占，原 owner 尝试释放
- **场景**：Client A 的锁 10s 过期 → Client B 抢到 → A 调用 Release
- **输入**：A 的 token 与 Redis 中当前 token 不一致
- **预期**：Lua 脚本返回 0，A 不删除 B 的锁
- **为什么重要**：这是分布式锁最经典的"误删他人锁"bug

#### 用例 3：Watchdog 在网络分区下的行为
- **场景**：续期过程中 Redis 不可达 15 秒后恢复
- **输入**：模拟网络中断 → 恢复
- **预期**：watchdog 检测到 TTL < 0 后主动退出，不僵尸续期
- **为什么重要**：你在追问中提到的改进点，需要测试保障

#### 用例 4：高并发抢锁的公平性
- **场景**：1000 goroutines 同时 Acquire
- **输入**：并发压测
- **预期**：只有一个成功，无 panic，无数据竞争
- **为什么重要**：go test -race 是否能通过？

#### 用例 5：Release 时的幂等性
- **场景**：同一把锁 Release 两次
- **输入**：连续调用 Release
- **预期**：第二次安全返回，不 panic，不删他人锁
- **为什么重要**：防御性编程，防止业务层重复调用

### 3. 测试金字塔评估
- 当前分布：单元 1 / 集成 0 / E2E 0
- 健康度：❌ 倒金字塔（只有少量单元测试，无集成和 E2E）
- 建议：至少补 3 个集成测试（用 miniredis 或 testcontainers）

### 4. 可测试性问题
- 🚫 时间硬编码：`time.Now()` 和 `time.After(3 * time.Second)` 无法 mock
- 🚫 Redis 客户端是具体类型而非接口，无法轻松替换
