## 1. 架构设计 — LangGraph 状态机  
  
### Q1: 为什么选择 LangGraph 而不是传统 API 链式调用或别的 Agent 框架？  
  
**参考答案：**  
  
三种方案对比：  
  
| 方案 | 状态管理 | 路由灵活性 | 可调试性 | 学习成本 |  
|------|---------|-----------|---------|---------|  
| 传统 API 链式（A→B→C） | 手动维护 session | 硬编码 if-else | 日志 | 低 |  
| LangGraph StateGraph | InMemorySaver 自动快照 | Conditional edges | LangSmith trace | 中 |  
| 通用 Agent 框架（LangChain Agent） | AgentExecutor | Tool-based | 好 | 中 |  
  
选 LangGraph 的核心原因：  
  
1. **有状态编排** — 传统的 API 链式调用需要手动传递 session 状态，LangGraph 的 `StateGraph` + `InMemorySaver` 把状态管理内建了。`SessionState` 作为单一数据源流过所有节点，每个节点只读写自己需要的字段。  
  
2. **条件路由** — `add_conditional_edges` 让路由决策变成纯函数（`start_router` → chat/agent/normal），比 JSON 配置路由表更灵活。  
  
3. **Checkpointer 自动快照** — 每次节点执行完成后自动保存状态，支持 resume/cancel/rewind。这对教学场景很重要（用户可能中途刷新页面）。  
  
4. **Agent 模式兼容** — LangGraph 的 `Command` 类型原生支持动态路由，使 agent 模式和普通模式共享同一个图。  
  
**缺点：**  
- 图结构复杂时调试困难（需要 LangSmith）  
- 节点间共享状态通过 SessionState，字段膨胀后维护成本高  
- 社区相对较新，最佳实践仍在演进  
  
**面试追问：** 如果面试官问「为什么不直接用 LangChain Agent？」—— 因为我们的图是确定性的（出题 → 判题 → 辅导 → 下一个节点），不是 Agent 式的「自己选工具」。确定性图比 Agent 循环更可预测、更易调试。  
  
### Q2: SessionState 的 reducers 是怎么设计的？用 `operator.add` 有什么坑？  
  
**参考答案：**  
  
```python  
submissions: Annotated[list[Submission], operator.add]  
tutor_messages: Annotated[list[Message], operator.add]  
```  
  
`operator.add` 自动做 `list1 + list2` 合并。好处：  
- 多节点并行写入时安全（虽然当前图是串行的）  
- 配合 checkpointer 的增量更新，不需要每次传递全量列表  
  
**坑：**  
1. **重复追加** — 如果节点写入了但 checkpointer 没更新（例如中途抛异常），下次重跑时字段会重复。解决方案：在节点入口做幂等检查。  
2. **无法删除** — `operator.add` 只支持追加，不支持删除。如果某个字段需要替换而非追加，就不能用这个 reducer。  
3. **字段膨胀** — 每轮循环追加，session 越长列表越大。当前没有做历史裁剪（future work）。  
  
### Q3: 图中共 11 个节点，路由是怎么组织的？如果要加一个新节点怎么做？  
  
**参考答案：**  
  
```  
┌─ 普通模式: planner → generator → wait_for_submit  
│             → judge → tutor → update_profile → critic → (循环)  
│  
├─ Chat 模式: chat_node → END（checkpointer 自动保存）  
│  
└─ Agent 模式: agent_dialog → planner → generator → wait_for_submit  
               → agent_judge → agent_tutor → (循环/END)  
```  
  
**加新节点的步骤：**  
1. 实现节点函数，签名 `(state: SessionState) -> Command`  
2. 在 `_build_graph()` 中 `builder.add_node("new_node", new_node_fn)`  
3. 添加边：`builder.add_edge("prev_node", "new_node")`  
4. 如果需要条件路由：`builder.add_conditional_edges("new_node", router_fn)`  
  
**面试考点：** 面试官可能问「那 start_router 的决策逻辑会越来越复杂吗？」—— 会。目前 start_router 只有 3 个分支。如果模式增多（如 debug_theatre 模式），应该拆成独立的 router 函数或配置表。

## 2. 判题系统 — 三阶段判题 + 对抗引擎  
  
### Q4: 为什么判题分三个阶段？为什么 Phase 3 不拦 AC？  
  
**参考答案：**  
  
```  
Phase 1 (基础判题) ─→ Phase 2 (对抗测试) ─→ Phase 3 (评审)  
      │                     │      └─ WA/RE/TLE → 辅导   └─ Fail → 辅导  
                                AC → 评审（不拦）  
```  
  
**设计意图：**  
- **教学效率** — 基础用例过不了的用户还没理解题，对抗没有意义  
- **渐进式反馈** — WA → L1~L4 提示；AC+对抗挂 → "你的解法在大规模下撑不住"  
- **评审不拦 AC 原则** — `judge.py` docstring 明确写了：「评审不拦 AC — AC 就是 AC，评审只影响下一题难度和用户画像」  
  
**面试追问：** 那评审还有什么用？—— 评审结果写入 profile delta，影响 planner 的下一题选择（难度调整、tag 推荐）。  
  
### Q5: 对抗测试为什么用混合策略（规则 + LLM）？怎么实现的？  
  
**参考答案：**  
  
两份对抗各有不同策略（`adversarial.py` docstring 有详细分析）：  
  
| 对抗类型 | 实现方式 | 为什么 |  
|---------|---------|-------|  
| 边界对抗 | 纯规则（`generate_boundary_cases`） | 边界是确定性组合，规则 100% 覆盖 |  
| 规模对抗 | LLM 描述特征 + 规则生成数据（`generate_scale_adversarial`） | LLM 出分布特征，规则拼数组 |  
  
**边界对抗（零 LLM 调用）：**  
- 读取题目的 constraints → 解析 n 的范围、值的范围  
- 枚举：空数组、单元素、极值、重复、负数、1000 元素快速侦测  
- 确定性保证：不会漏掉「空数组」  
  
**规模对抗（LLM+规则混合）：**  
```  
LLM 分析题目 + 用户代码 + AST 弱点分析结果  
    → 输出分布特征描述（JSON）：{"scale_description": "...", "n": 50000}  
规则引擎根据特征描述生成具体数组  
```  
  
为什么不只靠一种：  
- 纯规则拼的数组太假（全 1 数组测不出真 TLE）  
- 纯 LLM 拼大数组 token 爆炸（10⁵ 规模约 800KB）  
- 折中：LLM 只描述特征，规则生成数据  
  
**面试追问：** 单参数问题（如"找最大值"）为什么跳过规模对抗？—— 因为没有 target 参数，无法生成有意义的测试用例。  
  
### Q6: 基础判题等待后台用例生成的机制是怎么设计的？会有什么问题？  
  
**参考答案：**  
  
```python  
MIN_TC_FOR_FULL = 5  # <5 说明后台还没跑完（初始只有 2 个 sample）  
if len(test_cases) < MIN_TC_FOR_FULL:  
    for _ in range(20):  # poll up to 20s        _time.sleep(1)        problem_dict = get_problem_by_id(problem_id)        test_cases = problem_dict.test_cases        if len(test_cases) >= MIN_TC_FOR_FULL:            break```  
  
**设计点：**  
1. **非阻塞轮询** — 初始只有 2 个 sample，后台生成器在异步跑更多用例  
2. **渐进式判题** — 不等后台就跑完也能开始（用初始 2 个 sample）  
3. **超时兜底** — 20 秒后没生成完，直接用当前用例判  
  
**问题：**  
4. **sleep 阻塞线程** — `_time.sleep(1)` 阻塞了 graph 线程，20 秒内不能响应其他请求。应该换成 asyncio 的事件驱动。  
5. **竞态条件** — 如果两个请求同时判同一道题，可能都执行了轮询逻辑，浪费资源。  
6. **20 秒不够** — 在某些 LLM 生成缓慢的场景下，20 秒可能不够生成完整套件。  
  
**改进方案：** 用 asyncio.Event + WebSocket 推送「后台用例就绪」通知。  
  
### Q7: AST 弱点分析是怎么实现的？为什么不用 LLM？  
  
**参考答案：**  
  
`analyze_code_weakness()` 纯 AST 启发式：  
  
```python  
# 检测的弱点类型：  
has_nested_loop → "brute_force_n2"  # 嵌套循环 → O(n²)has_recursion and not has_memo → "recursion_no_memo"  # 递归无记忆化  
has_only_null_check → "boundary_only_null"  # 只检查了空输入  
has_dp_pattern → "dp_no_optimization"  # DP 但没优化空间  
```  
  
**为什么不用 LLM：**  
- 弱点分类是模式匹配问题，AST 启发式足够快且零成本  
- LLM 调用留给「生成对抗用例特征描述」那一步（需要语义理解）  
- 本项目将 LLM 视为**稀缺资源**，只用在需要语义理解的地方  
  
**弱点分析 → 规模对抗的链路：**  
```  
AST 分析 → 识别 "recursion_no_memo"        → generate_scale_adversarial 知道要测 deep_recursion        → LLM 描述分布特征时针对性更强  
```  
  
### Q8: 当前判题只支持 Python，怎么扩展到其他语言？  
  
**参考答案：**  
  
当前判题有两个路径：  
  
| 判题方式 | 当前支持语言 | 扩展到其他语言 |  
|---------|------------|--------------|  
| 本地 subprocess | 仅 Python | 按语言类型生成不同 harness（如 Java 用 javac + java，C++ 用 g++ + 运行） |  
| Judge0 远程判题 | Judge0 支持的语言 | 只需改 `language_id`（Judge0 CE 支持 50+ 语言） |  
  
**多语言 Judge0 实现：**  
```python  
# Judge0 语言 ID 映射  
LANGUAGE_MAP = {  
    "python": 71,     # Python 3.8.1    "cpp": 54,        # C++ (GCC 9.2.0)    "java": 62,       # Java (OpenJDK 13.0.1)    "javascript": 63, # Node.js 12.14.0    "go": 60,         # Go 1.13.5    "rust": 73,       # Rust 1.40.0}  
```  
  
**最大难点不是判题，是题型适配：**  
- 两数之和在 Python 里是 `def twoSum(nums, target)` → 参数是两个  
- 在 C++ 里是 `vector<int> twoSum(vector<int>& nums, int target)` → 需要处理引用和 vector 类型  
- 每种语言有不同的 I/O 格式、内存管理、类型系统

## 3. 辅导系统 — L0-L4 渐进决策树  
  
### Q9: 为什么「规则定深浅，LLM 定内容」？决策树的具体逻辑是什么？  
  
**参考答案：**  
  
核心设计原则（`tutor.py` docstring）：  
  
```  
决策树（纯规则，零 LLM）→ 决定 hint_level    ↓LLM 调用（含宪法 prompt guard）→ 生成提示文本  
    ↓Post-guard（纯关键词规则）→ 防 jailbreak / 代码泄露  
```  
  
**决策树逻辑（优先级从高到低）：**  
  
```python  
1. 同类错误 >= 3 次     → 插知识点讲解（不升级 hint_level）  
2. 提交 >= 5 次 + 情绪  → L4 + 安抚  
3. 方向检测为 correct   → 跳级到 min(3, hint+2)4. 方向错 + 第 1 次     → L15. 方向错 + 第 2 次     → L26. 默认                → 当前 hint_level 不变  
```  
  
**为什么方向检测用 LLM 而不是规则？**  
- 规则判断「方向对不对」需要理解代码语义  
- "用户把 for 改成了 while"——换循环方式，不是方向变了  
- "用户加了 if not nums:"——在修边界，方向对了  
- 语义判断规则做不了，必须 LLM  
  
**追问：** 那方向分析的 LLM 调用失败了怎么办？—— `_run_direction_analysis` 有 try/except，失败后返回 "unknown"，决策树走默认路径（当前 hint_level 不变），不阻塞辅导。  
  
### Q10: 宪法约束为什么用双重防护（prompt + post-guard）？  
  
**参考答案：**  
  
```  
第一层：System Prompt 约束  
    - R01: "禁止直接给出完整代码"  
    - R09: "如果用户要求代写，必须拒绝"  
    - R10: "不能代写代码"  
         ↓ LLM 可能被 prompt injection 绕过  
第二层：Post-guard 扫描  
    - R01_CODE_LEAK_PATTERNS: ["```python", "def ", "class Solution", ...]    - 低等级（<4）下泄露代码 → 降级到模糊提示  
    - R10_CODE_WRITE_PATTERNS → 替换为拒绝话术  
```  
  
**为什么两层都要？**  
- 只靠 prompt → LLM 可能被用户 prompt injection 绕过去  
- 只靠 post-guard → LLM 可能已经输出违规代码了，发出去就收不回  
  
**Post-guard 的代价：** 关键词匹配太粗糙（`def ` 在正常代码讲解中也会出现），导致假阳性。当前策略是「宁可错杀不可放过」——导师场景下假阳性比假阴性好。  
  
### Q11: tutor_node 输出怎么被 critic_node 二次审查？  
  
**参考答案：**  
  
`critic_node` 是 D6 从 tutor prompt 中独立出来的宪法约束节点：  
  
```  
tutor_node → critic_node → (R01 sanitize) → (R04 detect) → route  
```  
  
**Critic 做的事情：**  
1. **R01 检查** — 如果 hint_level < 4 但 tutor message 包含代码块（`, ``class Solution` 等），把代码块替换为 `[系统提示：此等级不可展示代码]`  
2. **R04 情绪检测** — 只记录日志，不改变路由（比 tutor 内的情绪检测更轻）  
3. **路由决策** — AC+对抗通过 → planner_node（下一题），否则 → wait_for_submit_node（等重提交）  
  
**独立 critic_node 的好处：** 宪法约束不混在辅导 prompt 里，易于独立维护和升级。  
  
### Q12: 情绪检测为什么用关键词而不是 LLM？  
  
**参考答案：**  
  
```python  
EMOTION_SIGNAL_KEYWORDS = ["不会", "放弃了", "烦", "太难了", "不想写了", ...]  
```  
  
检查最近 3 条消息：  
  
| 方案 | 延迟 | 成本 | 准确率 |  
|------|------|------|--------|  
| 关键词 | 0 ms | 0 | 中等（有误报） |  
| LLM 情绪分析 | ~1-2s | ~0.02 元/次 | 高 |  
  
**选择理由：**  
1. 关键词命中率足够覆盖常见负向情绪（"烦"、"放弃了"）  
2. 0 latency 意味着辅导体验不卡顿  
3. 误报可接受：如果用户说"我有点烦，但还能坚持"，关键词命中但不需要降级——这个误报不会引起问题  
4. LLM 做情绪识别，2 秒延迟 + token 成本，不划算

## 4. 用户画像 — Per-Tag ELO  
  
### Q13: 为什么从 5 维全局画像升级到 per-tag ELO 画像？  
  
**参考答案：**  
  
**旧版（DBProfile — SQLite）：**  
```python  
proficiency: float    # 全局 0-1stability: float      # 全局 0-1forget_days: int      # 全局  
common_errors: list   # 全局  
attempts: int         # 全局  
```  
  
**新版（UserProfile — InMemoryStore）：**  
```python  
prof: dict[str, float]              # per-tag 0-1（从 ELO 派生）  
prof_elo_raw: dict[str, float]      # per-tag ELO 1000-4000  
stab: dict[str, {window, variance}] # per-tag 稳定性  
forget: dict[str, {last_seen, decay}] # per-tag 遗忘  
errors: {_global, per_tag}          # 全局 + per-tag 错误指纹  
attempts: dict[int, AttemptRecord]  # per-problem 提交记录  
```  
  
**为什么必须 per-tag？**  
- 用户可能在双指针上很强（ELO 1800），在 DP 上很弱（ELO 1100）  
- 全局画像会平均化，导致推荐不精准  
- Per-tag 画像让 planner 能精准推荐「你最弱的 tag」  
  
**为什么用 ELO 而不是正确率？**  
- 正确率 80% 看不出是「刷简单题刷出来的」还是「难题也能做」  
- ELO 公式：`new_elo = old_elo + 64 * (1 - 1/(1+10^((prob_elo - old_elo)/400)))`  
- AC 一道 1800 分的难题加分多，AC 1200 分的简单题加分少  
- ELO 自平衡：用户 AC 多了分涨，涨了之后 AC 加分变少，直到稳定在真实水平  
  
**追问：** ELO 的 K=64 为什么选这个值？—— 初始值是经验值，K 越大单次影响越大（学习更快但波动大）。K=64 在 MVP 阶段表现合理。If 需要更稳定，可以降到 32。  
  
### Q14: profile_delta 模式和单 writer 纪律是怎么设计的？  
  
**参考答案：**  
  
```  
judge_node → state["profile_delta"]  (只挂增量，不直接写 store)tutor_node → state["profile_delta"]  (可修改/补充)  
update_profile_node → store.put()    (唯一写 store 的节点)  
```  
  
**设计原则（`profile/node.py` docstring）：**  
> ⚠️ 单 writer 纪律：只有这个 node 调 store.put()。判题/辅导哪怕想改画像，也只能挂 state["profile_delta"]。  
  
为什么？  
1. **写锁** — 避免多个节点同时写 store 造成竞态  
2. **可审计** — 所有画像更新都经过同一个节点，便于加日志/监控  
3. **纯函数** — `apply_delta` 是纯函数（输入 profile + delta → 输出新 profile），易于测试  
  
### Q15: 新版本画像存在 InMemoryStore，为什么不同时持久化到 SQLite？  
  
**参考答案：**  
  
当前是**双写模式**（`update_profile_node`）：  
  
```python  
store.put(STORE_NS, user_id, updated)          # InMemoryStore（LangGraph 内）  
save_user_profile_v2(updated)                  # SQLite（供前端展示）  
```  
  
**为什么 InMemoryStore + SQLite 双写？**  
- InMemoryStore 与 LangGraph 的 store 接口兼容，未来切换持久化 store 成本低  
- SQLite 保存一份副本，供 `GET /admin/profile/v2` 接口查询  
  
**问题：**  
- 双写可能有短暂不一致（SQLite 写失败不阻塞主流程）  
- InMemoryStore 重启丢失  
  
**未来方案：** 切到 LangGraph 的 `SQLiteStore` 或 `RedisStore`，去掉双写。  
  
### Q16: 5 维画像各维度的权重和优先级怎么设计？  
  
**参考答案：**  
  
| 维度 | 用途 | 更新频率 | 优先级 |  
|------|------|---------|-------|  
| prof (xl) | 选下一题 tag | 每次提交 | 最高 |  
| stab (稳定性) | 是否加难度 | 每次提交 | 高 |  
| forget (遗忘) | 是否需要复习 | 每次提交（被动衰减） | 中 |  
| errors (错误指纹) | 出题时避开用户的弱项类型 | 每次 WA | 低（累积） |  
| attempts (提交记录) | 防止重复出题 | 每次提交 | 低 |  
  
**Planner 的决策逻辑：**  
```  
1. 在所有 tag 中找 prof 最低的  
2. 如果该 tag 的 stab 方差 > 0.3 → 降难度  
3. 如果该 tag 的 forget.decay < 0.3 → 优先复习  
4. 如果 errors 显示用户总是忽视边界 → 出边界密集型题  
```

## 6. API 设计 — FastAPI 路由 + SSE 流式  
  
### Q19: 为什么用 SSE 流式而不是 WebSocket？  
  
**参考答案：**  
  
| 特性 | SSE | WebSocket |  
|------|-----|----------|  
| 单向（服务端→客户端） | ✅ 原生 | 全双工 |  
| 浏览器原生支持 | EventSource API | WebSocket API |  
| 自动重连 | ✅ 原生 | 需手动实现 |  
| 传递二进制数据 | ❌（但用不到） | ✅ |

3. 自动重连是 JS 原生的，不需要额外代码  
  
**`useSSE.ts`** 的实现：  
```typescript

const reader = resp.body.getReader();  
// 解析 SSE data: 行 → onToken(token)  
```

**参考答案：**  
  
模块化路由设计：  
  
```  
api/  
├── main.py           # FastAPI app + middleware + router include  
├── deps.py           # init_graph() / get_graph() 单例

2. 多人协作时不冲突  
3. 加新功能只需加新 router 文件，在 main.py 加一行 `app.include_router`

### Q21: 提交代码后，前端怎么知道判题结束的？  
  
**参考答案：**  
  
当前是**两步走**：  
  
```  
POST /session/{sid}/submit → 返回 { verdict, hint_level, tutor_message }    ↓ 快速响应（~1-2s，LLM 返回前）  
GET  /session/{sid}/state  → 轮询完整状态（包括 tutor_messages、submissions）  
```  
  
**为什么不是一次响应完成？**  
- LLM 生成辅导提示需要 ~2-5s，如果等 LLM 返回再响应 HTTP 请求，用户体验差  
- 所以 submit 先返回快速结果（verdict），前端立即知道「过了还是没过」  
- 辅导提示通过 `GET /session/{sid}/state` 轮询或 SSE 推送  
  
**轮询的代价：** 前端每秒轮询 `/state` 一次，如果 1000 个用户同时在用，后端 QPS 会很高。改进方案：改为后端 SSE 推送「状态更新」事件。

## 8. 沙箱安全 — 代码执行  
  
### Q25: 本地 subprocess 怎么执行用户代码？安全性怎么保证？  
  
**参考答案：**  
  
```  
用户代码 → _build_harness(code, test_cases) → tempfile .py         → subprocess.run(  # 当前没有 sandbox 隔离  
             [sys.executable, tmp.name],             timeout=timeout + HARNESS_TIMEOUT,             capture_output=True,           )         → 解析 stdout 中的 RESULT: 行  
         → 清理 tempfile```  
  
**当前的安全措施：**  
1. **subprocess 超时** — `timeout + HARNESS_TIMEOUT`，防止无限循环  
2. **输入注入** — 用户代码通过 stdin 或参数传递测试用例，不直接拼接  
3. **tmpfile 清理** — `finally: os.remove(tmp.name)`  
4. **Judge0 隔离** — 生产环境通过 Judge0 的 isolate 沙箱（cgroup-v2 软限制）  
  
**当前没做的（风险）：**  
- ❌ 没有进程级隔离（用户代码可以 `import os` 执行系统命令）  
- ❌ 没有文件系统隔离（可以读写 tmp 目录外的文件）  
- ❌ 没有内存限制（可能 OOM）  
  
**生产环境方案：** 强制走 Judge0（Docker 容器隔离）+ cgroup 内存/CPU 限制。  
  
### Q26: Judge0 harness 是怎么适配 LeetCode 风格的 class Solution 风格的？  
  
**参考答案：**  
  
```python  
# ds.py 的 INJECT_PROLOGUE 注入到全局命名空间  
from typing import *  
class ListNode: ...    # 链表节点  
class TreeNode: ...    # 二叉树节点  
class Node: ...        # N 叉树节点  
```  
  
**harness 生成逻辑（`runner.py` 的 `_build_harness`）：**  
1. 在用户代码前注入 INJECT_PROLOGUE  
2. 用 `inspect.getmembers(sol, predicate=inspect.ismethod)` 找到 Solution 类的第一个 public 方法  
3. 遍历 test_cases，对每个用例：`ast.literal_eval(input_args)` → 调用 method → 比较输出  
4. 每行输出 `RESULT: {json}` 格式，供主进程解析  
  
**面试追问：** 如果用户代码不是 `class Solution` 风格呢？—— 当前假设所有代码都是 `class Solution` 风格。如果要支持自由函数（如 `def twoSum(nums, target)`），需要修改 harness 的发现逻辑。

## 9. 数据持久化 & 存储设计  
  
### Q27: problems 表为什么用 JSON 列而不是关系表？  
  
**参考答案：**  
  
`problems` 表的关键字段：  
  
```sql  
test_cases_json      TEXT     -- JSON: [{"input_args":[],"expected_output":""}]  
visible_test_cases_json TEXT  -- JSON  
adversarial_spec_json TEXT    -- JSON  
constraints_json     TEXT     -- JSON  
alternative_solutions TEXT    -- JSON  
```  
  
**为什么用 JSON 列？**  
1. **测试用例是嵌套结构** — 每个测试用例有 input_args（数组）、expected_output（字符串）、is_hidden（布尔），用关系表需要 2-3 张表（problems, test_cases, inputs）  
2. **查询模式单一** — 永远是一次性读/写全部 test cases（没有"按 input_args 查询"的需求）  
3. **JSON 简洁** — 序列化/反序列化在 Python 侧由 Pydantic + json.dumps 处理，比 ORM 关系查询快  
  
**代价：** 不能 SQL 查询 test_cases 内容（"找到包含负数输入的题目"）。但目前没有这种需求。  
  
### Q28: _with_conn 装饰器的设计模式是什么样的？  
  
**参考答案：**  
  
```python  
def _with_conn(fn):  
    conn = _get_conn()    try:        result = fn(conn.cursor())        conn.commit()        return result    except Exception:        conn.rollback()        raise    finally:        conn.close()```  
  
**设计点：**  
1. **try/commit/except/rollback/finally** — 确保连接始终关闭，不会泄漏  
2. **WAL 模式** — `PRAGMA journal_mode=WAL`，允许并发读  
3. **sqlite3.Row** — `row_factory = sqlite3.Row`，按列名访问而非索引  
  
**为什么不用 ORM（如 SQLAlchemy）？**  
- SQLite 场景简单（5-6 张表），ORM 的 mapping 开销 > 收益  
- 本项目的 SQL 查询都是简单的 CRUD，拼字符串就可维护  
- 如果未来切到 PostgreSQL，再加 SQLAlchemy

## 11. 错误处理 & 可靠性  
  
### Q32: LLM 调用失败怎么降级？  
  
**参考答案：**  
  
全项目 4 处 LLM 调用的降级策略：  
  
| 场景 | LLM 用途 | 降级行为 |  
|------|---------|---------|  
| 出题（generator） | 生成题目 + 参考解 | 重试 2 次 → 切到静态题库 |  
| 辅导（tutor） | 生成提示 | 用 `_FALLBACK_HINTS` 模板消息 |  
| 方向分析（tutor） | 判断用户改的方向 | 返回 "unknown"，决策树走默认路 |  
| 规模对抗（adversarial） | 描述分布特征 | 用硬编码默认值 |  
  
**Generator 出题降级（关键链路）：**  
```python  
for attempt in range(1, MAX_ATTEMPTS + 1):  # 最多 2 次  
    try:        problem_obj = generate_problem(...)        # 自验证...  
    except Exception:        continue  # 重试  
else:  
    problem_dict = get_static_problem()  # 从预置题库取  
```  
  
**追问：** 静态题库有多大？—— 当前只有 5 道预置题。如果用户重试时遇到相同的静态题，体验不好。需要扩展静态题库。  
  
### Q33: 画像更新失败为什么不阻塞主流程？  
  
**参考答案：**  
  
```python  
try:  
    update_profile_on_result(topic=..., verdict=verdict)except Exception:  
    logger.warning("Profile update failed (non-fatal)", exc_info=True)  
```  
  
**为什么是非致命错误？**  
- 画像不影响当前这道题的判题和辅导  
- 如果画像更新失败，最坏结果是下一题推荐不准  
- 用户不能因为画像写库失败而看不到辅导反馈  
  
**非致命 vs 致命错误的分界：**  
- **致命**：LLM 出题失败（用户没题做）、判题失败（用户不知道结果）→ 需要降级或报错  
- **非致命**：画像更新失败、进度更新失败、后台用例生成失败 → 记日志，不中断用户

## 12. 系统设计题  
  
### Q34: 如果每天有 10 万用户使用，架构需要怎么改？  
  
**参考答案：**  
  
当前架构瓶颈分析：  
  
| 组件 | 当前方案 | 单机上限 | 扩展方案 |  
|------|---------|---------|---------|  
| Session 状态 | InMemorySaver | ~1000 session | Redis / Postgres checkpointer |  
| 用户画像 | InMemoryStore | 重启丢失 | SQLiteStore / RedisStore |  
| LLM 调用 | 同步 invoke | ~10 RPM | 多 provider + 请求排队 + 缓存 |  
| Judge0 | 本地单进程 | 单 worker | 容器化 + 消息队列 |  
| 数据库 | SQLite WAL | ~100 并发写 | PostgreSQL + 连接池 |  
  
**扩展架构设计：**  
```  
[Load Balancer]  
       │[API Server 1] [API Server 2] ... [API Server N]  
       │               │       └─────── [Redis] ──────┘   # Session 状态 + 消息队列  
                       │               [PostgreSQL]        # 用户数据 + 题目  
                       │               [Judge0 Cluster]    # Docker 容器判题集群  
                       │               [LLM Proxy]          # 多 provider + 限流 + 缓存  
```  
  
**最大的挑战不是技术是成本：** LLM API 调用是主要成本。10 万用户 × 平均每 session 3 次 LLM 调用 × 每次 ~0.05 元 = 每天 ~1.5 万元。缓存策略和降级策略关键。  
  
### Q35: 如果后端重启了，正在进行的 session 怎么办？  
  
**参考答案：**  
  
当前：**全部丢失**  
  
```python  
checkpointer = InMemorySaver()   # session 状态丢失  
store = InMemoryStore()          # 画像数据丢失  
```  
  
**影响分析：**  
- 正在做的题 → 用户需要重新创建 session  
- 用户画像（新版 per-tag）→ 丢失，从零开始  
- 用户画像（旧版 5 维 SQLite）→ 保留  
- 题目数据 → 保留（SQLite）  
  
**改进方案（按优先级）：**  
1. 短期：session 状态做 `checkpointer` 持久化到 `.sqlite` 文件  
2. 中期：画像切到 SQLiteStore  
3. 长期：用 Postgres 做持久化，支持水平扩展  
  
### Q36: 怎么防止用户恶意刷题（script 提交）？  
  
**参考答案：**  
  
当前**没有任何防护**。应该加的防护：  
  
| 防护措施 | 实现 | 影响 |  
|---------|------|------|  
| 提交频率限制 | 每 session 每 5s 最大 1 次 | 阻止脚本提交 |  
| 代码相似度检测 | 与上一次提交的 diff 大小 | 防止刷分 |  
| 总提交次数限制 | 每 session 最大 30 次 | 阻止无限重试 |  
| IP 限流 | API 层 rate limiter | 防止 DDoS |  
  
**注意：** 教学场景和比赛场景的限流策略不同。教学场景希望鼓励多尝试（"再改一次"），所以限流比竞赛场景宽松。

## 13. 未来扩展方向  
  
### Q37: 多语言支持 — 怎么扩展到 C++/Java/JS/Go/Rust？  
  
**参考答案：**  
  
**需要改动的模块：**  
  
| 模块 | 改动 |  
|------|------|  
| Judge0 language_id | 加 `LANGUAGE_MAP` 映射表 |  
| 出题 LLM prompt | 多语言模板、每种语言有不同的 starter code |  
| Harness | 每种语言有不同的测试用例执行体 |  
| 前端编辑器 | 根据语言切换 Monaco Editor 语法高亮 |  
| 对抗测试 | AST 分析只对 Python 有效，其他语言需另写分析器 |  
  
**难度排序（从低到高）：**  
1. **Judge0 判题** — 最容易，Judge0 CE 原生支持 50+ 语言  
2. **前端编辑器** — Monaco Editor 支持所有主流语言  
3. **LLM 出题** — prompt 加 language 参数即可  
4. **对抗测试** — 最难的：Python AST 分析器不能跨语言，需要为每种语言写分析器  
  
**MVP 策略：** 先支持 Judge0 判题 + 前端编辑器切换，AST 分析暂时只对 Python 生效。C++/Java 用户也能做题，只是对抗测试精度降低。  
  
### Q38: 对抗测试平台化 — 怎么让社区的对抗用例贡献进来？  
  
**参考答案：**  
  
当前对抗用例是自动生成的（规则 + LLM）。社区化思路：  
  
```  
对抗用例注册表（SQLite 或 JSON 文件）  
├── 内置规则（当前：边界枚举 + 规模 LLM）  
├── 社区贡献  
│   ├── 按题目 ID 挂载  
│   ├── 有难度等级和标签  
│   └── 自动 CI 验证有效性  
└── 平台精选  
    └── 高投票、高覆盖率的对抗用例  
```  
  
**社区对抗用例的格式：**  
```json  
{  
    "problem_id": 42,  
    "author": "user_xxx",  
    "test_case": {  
        "input_args": ["[1,1,1,1,1,2]", "2"],  
        "expected_output": "[5]",  
        "explanation": "重复元素 + target 在末尾"  
    },  
    "votes": 12,  
    "verified": true  
}  
```  
  
**为什么社区化有价值？** 自动生成的对抗用例有限（基于约束启发式），社区贡献的用例更贴近实际面试中遇到的边界情况。  
  
### Q39: 知识图谱 — 怎么从平面 tag 列表升级为知识图谱？  
  
**参考答案：**  
  
当前 tag 是平面的（"数组"、"双指针"、"动态规划"），planner 轮转选择。  
  
**知识图谱设计：**  
  
```  
数组 + 哈希表 ──→ 双指针 ──→ 滑动窗口 ──→ 前缀和  
    │    └──→ 排序 ──→ 二分查找 ──→ 二分答案  
                    │                    └──→ 旋转数组 ──→ 二叉搜索树  
    │动态规划 (easy) ──→ DP (medium) ──→ DP (hard)    │    └──→ 记忆化搜索 ──→ 区间 DP ──→ 树形 DP```  
  
**Planner 怎么用知识图谱：**  
1. 用户 AC 了「数组+哈希表」→ 推荐下一题「双指针」（图谱中的后继节点）  
2. 用户在「双指针」上失败了 3 次 → 推荐回溯到「数组+哈希表」（巩固前置知识）  
3. 用户 7 天没练「动态规划」→ 推荐「DP easy」（防遗忘）  
  
**数据存储：** SQLite `knowledge_graph` 表：  
```sql  
CREATE TABLE knowledge_graph (  
    id INTEGER PRIMARY KEY,    prereq_tag TEXT NOT NULL,   -- 前置知识 (如 "数组")  
    postreq_tag TEXT NOT NULL,  -- 后续知识 (如 "双指针")  
    difficulty_shift TEXT       -- easy → medium);  
```  
  
### Q40: 自托管 LLM — 如果 LLM API 涨价了，怎么切到本地模型？  
  
**参考答案：**  
  
当前通过 `config.py` 的 `LLM_CONFIGS` 实现了**模型无关抽象层**：  
  
```python  
get_llm("agnes", temperature=0.4)  # 通过别名调用，不关心具体模型  
LLM_CONFIGS["agnes"] = {  
    "model": "deepseek-coder",    "model_provider": "openai",     # 兼容 OpenAI API 格式  
    "base_url": "http://localhost:11434/v1",  # Ollama    "api_key": "ollama",            # 本地模型不需要真实 key}  
```  
  
**切换方案：**  
  
| 模型级别 | 当前 | 替代方案 | 成本 |  
|---------|------|---------|------|  
| 核心 LLM（出题 + 辅导） | 云端 API | ollama + deepseek-coder / Qwen2.5 | 本地 0 元 |  
| 辅助 LLM（对抗 + 方向分析） | 云端 API | 同上（复用） | 本地 0 元 |  
| 降级 fallback | 静态题库 | 同 | 0 元 |  
  
**切换不成功的原因：**  
1. **质量差距** — 本地 7B 模型 vs 云端 70B+ 模型，出题质量和辅导深度差一档  
2. **延迟** — 本地 GPU 推理速度取决于硬件，CPU 推理可能比云端慢 10x  
3. **并发能力** — 云端有数千并发 capacity，本地 1 张 GPU 只能同时服务 1-2 个请求  
  
**面试追问：** 那你们怎么选？—— 混合方案：核心出题和辅导用云端（质量优先），对抗用例生成和方向分析用本地模型（成本优先，且这些任务对质量不敏感）。  
  
### Q41: 作业系统 — 老师怎么布置题目给学生？

需要加的角色和权限模型：

权限模型（3 级）：  
├── 学生 → 做题、看自己的画像  
├── 老师 → 布置作业、看学生作业完成情况  
└── 管理员 → 管理全局题库、管理用户  
  
作业系统（新增模块）：  
├── assignment (id, teacher_id, title, deadline, problem_ids, status)

**面试追问：** 作业系统的核心设计难题是什么？—— 是「防抄袭」，不是功能实现。学生提交的代码可能是抄的，老师需要看到「这道题用户重试了几次」「AC 前看了多少提示」这些元数据来判断。  
  
### Q42: 面试模式 — 怎么模拟真实面试环境？  
  
**参考答案：**  
  
当前有 `mode = "interview"` 字段但未实现。完整面试模式设计：  
  
```  
┌─ 限时 45 分钟  
├─ 随机抽题（不按画像推荐）  
├─ 看不到判题结果（只有面试官知道你对没对）  
├─ 不能多次提交（一次通过或一次放弃）  
├─ 录音/打字记录 → 面试复盘  
└─ 面试结束后生成报告：  
    ├─ 这道题的代码质量（复杂度、边界处理）  
    ├─ 花了多长时间  
    ├─ 有没有用到面试官期待的算法  
    └─ 面试技巧评分（沟通、思考过程、Debug 能力）  
```  
  
**和普通模式的区别：**  
  
| 维度 | 普通模式 | 面试模式 |  
|------|---------|---------|  
| 反馈 | 即时 | 结束后 |  
| 提交次数 | 不限 | 1 次 |  
| 题目选择 | 按画像推荐 | 随机 |  
| 时间限制 | 无 | 45 分钟 |  
  
**追问：** 面试模式的判题怎么不暴露结果？—— 用户提交代码后走完整的 judge 流程（Phase 1-3），但结果写入 report 而不是返回给用户。用户看到的是"已提交，面试结束可查看报告"。  
  
### Q43: LLM Prompt A/B 测试 — 怎么评估改 prompt 的效果？  
  
**参考答案：**  
  
需要加实验框架：  
  
```  
实验框架设计：  
├── experiment (id, name, prompt_variant, started_at, ended_at)  
├── experiment_assignment (experiment_id, session_id, variant)  
└── experiment_metric (session_id, metric_name, metric_value)  
  
监控指标：  
├── 用户留存率（做完一题后是否继续做第二题）  
├── 平均提交次数（过少说明太简单，过多说明辅导不到位）  
├── 平均 hint_level 变化速度（辅导效率）  
├── 用户挫败情绪检测频率（prompt 改差了的信号）  
└── AC 率（这个偏噪声，因为题目难度不同）  
```  
  
**MVP 实现：** LLM_CONFIGS 中加 `prompt_variant` 参数，不同迭代的 prompt 由 `config.py` 的版本控制，人工对比指标。  
  
**为什么 A/B 测试对 LLM 产品更难？**  
1. LLM 每次输出不同，非确定性，需要更大的样本量  
2. prompt 改 3 个字可能改变输出风格，但用户是否 feel 到很难量化  
3. 外部因素（API 模型升级、用户群体变化）会污染实验结果  
  
### Q44: 强化学徒 — 怎么用 RL 优化辅导策略？  
  
**参考答案：**  
  
当前 `_decide_hint_level` 是硬编码规则树。未来可以用 RL 优化：  
  
**State（环境状态）：**  
```python  
{  
    "current_hint_level": 0-4,    "submission_count": int,    "same_error_count": int,    "emotion_detected": bool,    "proficiency": float,  # 画像中该 tag 的熟练度  
    "difficulty": "easy|medium|hard",}  
```  
  
**Action（决策）：**  
```python  
["提升 hint_level", "维持 hint_level", "插讲解", "给 AC 后直接下一题", ...]  
```  
  
**Reward（奖励信号）：**  
```python  
+1.0  用户 AC+0.5  hint_level 提升后下一次提交有进步  
-0.5  用户提交后情绪变差  
-1.0  用户放弃  
-0.2  hint_level 太快（用户还没思考就给了答案）  
```  
  
**难点：**  
1. **冷启动** — RL 需要大量数据训练，初期还是得用规则树  
2. **延迟奖励** — 用户 AC 是最终 reward，但中间可能有 10+ 步决策，credit assignment 困难  
3. **安全约束** — RL 可能学到"给立刻答案用户开心"的策略，违反教学原则  
  
**实用方案：** 用 RL 调规则树的参数（如 `_REPEAT_THRESHOLD` 从 3 改为 4 或 2），不直接学动作。  
  
### Q45: 作弊检测 — 怎么判断用户是不是在抄答案？  
  
**参考答案：**  
  
多层检测：  
  
| 层 | 检测方式 | 效果 |  
|----|---------|------|  
| 1. 提交时间 | < 3s AC → 可能粘贴 | 低 |  
| 2. 代码相似度 | 与 optimal_solution 的 edit distance < 10% | 中 |  
| 3. 编码风格变化 | 突然换变量命名风格、缩进风格 | 中 |  
| 4. 打字速度 | 前端记录 keystroke 间隔（前端才能做） | 高 |  
  
**实现（后端）：**  
```python  
def detect_plagiarism(code: str, optimal: str) -> dict:  
    # 1. 归一化（去除注释、空白）  
    norm_code = re.sub(r'#.*', '', code).strip()    norm_opt = re.sub(r'#.*', '', optimal).strip()  
    # 2. edit distance    similarity = SequenceMatcher(None, norm_code, norm_opt).ratio()  
    # 3. 判断  
    if similarity > 0.9:        return {"suspicious": True, "reason": "code_too_similar", "score": similarity}    return {"suspicious": False}  
```  
  
**追问：** 如果用户自己一题一题打但思路和官方一模一样呢？（检测 False Positive）—— 这是作弊检测最大的难题。所以检测结果不能用来"惩罚"用户，而是作为老师查看作业时的参考标记。
