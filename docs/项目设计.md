# Skills Engine 项目设计文档

## 一、项目概述

### 1.1 目标

构建一个兼容 Claude Code **Agent Skills 开放标准**的 skills 解析器和路由器，使任何 AI agent 系统能够：

- 发现和加载 Claude Code 生态中的 skills（SKILL.md 格式）
- 根据用户输入智能匹配 relevant skills
- 执行 skill 中的动态上下文注入、参数替换、权限控制
- 将 skill 路由到正确的 AI 系统或子代理执行

### 1.2 为什么做

Claude Code 的 skills 规范已经是开放标准（Agent Skills），被多个 AI 工具采纳。但大多数工具只支持简单的 SKILL.md 解析，缺少完整的**匹配引擎 + 路由分发 + 动态注入**能力。本项目填补这一空白。

### 2.4 Pi 的局限性

1. **没有 skills 发现机制** - 不会扫描 `.claude/skills/` 目录
2. **没有 skills 匹配逻辑** - 无法根据用户意图自动加载 skill
3. **frontmatter 解析过于简单** - 只解析 YAML，不支持 Claude Code 的所有 frontmatter 字段（如 `when_to_use`、`paths`、`shell` 等）
4. **没有动态注入** - 不支持 `` !command `` 语法
5. **没有 skills 缓存** - 每次都要重新解析 SKILL.md
6. **工具注册和 skills 路由是两套系统** - 没有统一抽象

```
├── cache/                # 缓存层
│   ├── __init__.py

└── types/                # 类型定义
    └── __init__.py
```

### 3.2 数据流

```
用户输入
  │
  ▼
[Scanner] 扫描所有 skills 目录
  │
  ▼
[Matcher] 匹配 relevant skills
  │  ├─ keyword_matcher: description/when_to_use 关键词匹配
  │  └─ semantic_matcher: embedding 向量相似度（可选）
  │
  ▼
[Engine] 执行匹配的 skill
  │  ├─ ContextInjector: 执行 !command 注入动态上下文
  │  ├─ ParamSubstitutor: 替换 $ARGUMENTS, $0, $1
  │  └─ PermissionChecker: 检查 allowed-tools
  │
  ▼
[Routed to AI System]
  │  ├─ 直接执行（task skill）
  │  ├─ 子代理 fork（context: fork）
  │  └─ 返回给上层 agent
```

### 3.3 核心数据模型

```python
@dataclass
class SkillMetadata:
    """Skill 的前元数据"""
    name: str                          # 技能名称（目录名）
    description: str                   # 描述，用于匹配
    when_to_use: str = ""              # 额外触发条件
    disable_model_invocation: bool = False  # 禁止自动触发
    user_invocable: bool = True        # 是否对用户可见
    allowed_tools: list[str] = field(default_factory=list)
    disallowed_tools: list[str] = field(default_factory=list)
    context: str = "inline"            # "inline" or "fork"
    agent: str = "general-purpose"     # Explore, Plan, 或自定义
    paths: list[str] = []              # 文件路径限制
    shell: str = "bash"                # bash 或 powershell
    arguments: list[str] = []          # 命名参数定义
    effort: str = "inherit"            # low/medium/high/xhigh/max
    model: str = "inherit"             # 模型覆盖

@dataclass
class Skill:
    """完整的 Skill 对象"""
    metadata: SkillMetadata
    content: str                       # Markdown 正文
    directory: Path                    # Skill 所在目录
    supporting_files: list[Path]       # 支持文件列表
    compiled_content: str = ""         # 编译后的最终内容（缓存用）

@dataclass
class MatchResult:
    """匹配结果"""
    skill: Skill
    score: float                       # 匹配分数 0-1
    method: str                        # "keyword" or "semantic"
    arguments: dict = field(default_factory=dict)  # 解析后的参数
```

## 四、实现方案对比

### 4.1 方案 A：基于 Pi 扩展（推荐）

**思路**：在 pi 的 `coding-agent/utils/` 下新增 `skills/` 模块，复用现有的 frontmatter 解析、工具注册、会话管理。

**优点**：
- 复用已有基础设施（frontmatter 解析、LLM 抽象层、工具注册）
- 与 pi 的代码风格一致
- 可以后续合并到 pi 上游
- Python 生态成熟，YAML/Markdown 解析库丰富

**缺点**：
- 需要深入理解 pi 的代码结构
- 可能与 pi 的更新产生冲突
- 如果 pi 不接纳贡献，需要维护 fork

**工作量**：约 2-3 周（全职）

### 4.2 方案 B：独立项目

**思路**：新建一个独立的 Python 包，不依赖 pi，但兼容 Claude Code 的 skills 规范。

**优点**：
- 完全自主控制，不受 pi 约束
- 可以更快迭代，不需要协调上游
- 可以独立发布到 PyPI

**缺点**：
- 需要自己实现 frontmatter 解析（虽然很简单）
- 失去 pi 的 LLM 抽象层和工具注册框架
- 与 pi 的集成需要额外工作

**工作量**：约 3-4 周（全职）

### 4.3 方案 C：TypeScript 版（与 pi 同步）

**思路**：同时开发 TypeScript 版本，与 pi 的原生实现保持一致。

**优点**：
- 与 Claude Code 原生实现最接近
- 可以直接集成到 pi TypeScript 版

**缺点**：
- 开发量大（需要维护 Python + TypeScript 两个版本）
- TypeScript 生态不如 Python 成熟

**工作量**：约 4-6 周（全职）

### 4.4 推荐方案

**方案 A + C 的组合**：
1. 先用 Python 实现核心引擎（方案 A）
2. 确保接口设计足够抽象，可以移植到 TypeScript
3. 后续视情况开发 TypeScript 版本

## 六、关键技术决策

### 6.1 匹配策略

| 策略 | 适用场景 | 优点 | 缺点 |
|------|----------|------|------|
| 关键词匹配（基础） | 所有场景 | 快速、简单、可解释 | 精度有限 |
| Embedding 语义匹配（增强） | 复杂意图 | 理解语义、泛化能力强 | 需要额外依赖、较慢 |
| 混合匹配（推荐） | 生产环境 | 兼顾速度和精度 | 实现复杂 |

**推荐实现**：
- MVP 阶段只用关键词匹配
- Phase 3 加入 embedding 语义匹配作为可选增强
- 提供 `MatchStrategy` 接口，用户可以切换

### 6.2 动态注入安全性

`` !command `` 执行存在安全风险，需要：
1. **沙箱执行** - 限制命令白名单
2. **超时控制** - 防止命令挂起
3. **输出过滤** - 防止注入攻击
4. **权限检查** - 只在 allowed-tools 包含 Bash 时才执行

### 6.3 缓存策略

```python
class SkillCache:
    """Skill 编译缓存
    
    缓存键: skill_directory_hash
    缓存值: compiled_skill (SkillMetadata + compiled_content)
    失效策略: 
      - 文件修改时间变化
      - 手动刷新
      - TTL（可选）
    """
```

## 七、扩展性设计

### 7.1 插件化架构

```python
class SkillMatcher(ABC):
    """匹配器接口，支持自定义实现"""
    @abstractmethod
    def match(self, user_input: str, skills: list[Skill]) -> list[MatchResult]:
        pass

class KeywordMatcher(SkillMatcher):
    """关键词匹配实现"""
    pass

class SemanticMatcher(SkillMatcher):
    """语义匹配实现"""
    pass

class CustomMatcher(SkillMatcher):
    """用户自定义匹配器"""
    pass
```

### 7.2 可扩展的 Router

```python
class SkillRouter:
    """路由分发器，支持多种执行模式"""
    
    def route(self, match_result: MatchResult) -> ExecutionMode:
        """根据 skill 配置选择执行模式"""
        if match_result.skill.metadata.context == "fork":
            return ExecutionMode.SUBAGENT_FORK
        elif match_result.skill.metadata.disable_model_invocation:
            return ExecutionMode.USER_INVOCABLE
        else:
            return ExecutionMode.INLINE
```

## 八、已知缺陷和限制

### 8.1 当前设计的缺陷

| 缺陷 | 影响 | 缓解措施 |
|------|------|----------|
| 关键词匹配精度有限 | 可能误匹配 | 引入 embedding 语义匹配 |
| 动态注入安全风险 | 命令注入 | 沙箱执行 + 白名单 |
| 大量 skills 时匹配慢 | 性能问题 | 缓存 + 索引 |
| 不支持 hooks | 功能不完整 | Phase 4 扩展 |
| 不支持 plugins | 功能不完整 | Phase 4 扩展 |

### 8.2 Claude Code Skills 规范的灰色地带

1. **嵌套 skill 的优先级** - 当多个 skill 匹配同一文件时，如何选择？
2. **compaction 后的 skill 行为** - 对话压缩后 skill 是否重新加载？
3. **skill 描述的截断** - 超过 1536 字符的描述如何处理？
4. **skillOverrides 的兼容性** - 如何支持 Claude Code 的 override 机制？

### 8.3 技术限制

1. **Python 的 subprocess 限制** - 在某些平台（Windows）上 subprocess 行为不一致
2. **YAML 解析的边界情况** - 复杂的 YAML frontmatter 可能解析失败
3. **Markdown 渲染** - skill 内容中的 Markdown 需要正确渲染

## 九、Q&A 自问自答

### Q1: 为什么不直接用 Claude Code 的 SDK？

**A**: Claude Code 的 Agent SDK 主要面向编程调用 Claude Code CLI，不是面向 skills 解析的。而且 Agent SDK 需要 Claude 订阅，不适合开源项目。我们的目标是做一个**通用的 skills 解析器**，可以被任何 AI 系统使用。

### Q2: 为什么要基于 pi？为什么不从零开始？

**A**: 
- pi 已经有 frontmatter 解析、工具注册、LLM 抽象层等基础设施
- 复用可以减少重复劳动
- 与 pi 的代码风格一致，便于后续贡献上游
- 但如果不适合，完全可以独立出来

### Q3: 匹配引擎的精度如何保证？

**A**: 
- MVP 阶段用关键词匹配，精度有限但速度快
- Phase 3 引入 embedding 语义匹配，精度显著提升
- 可以提供混合匹配策略，结合两者优势
- 用户也可以通过 `when_to_use` 字段精确控制触发条件

### Q4: 动态注入的安全风险怎么控制？

**A**: 
- 命令白名单机制：只允许执行预定义的命令
- 超时控制：每个命令最多执行 5 秒
- 输出过滤：去除可能的恶意内容
- 权限检查：只有 `allowed-tools` 包含 Bash 时才执行

### Q5: 如何与现有的 pi 工具系统集成？

**A**: 
- 复用 `pi_agent/tools/` 的工具注册框架
- Skills 的 `allowed-tools` 字段映射到工具注册表的权限
- Skill 执行时通过 `AgentSession` 调用对应的工具

### Q6: 如果 pi 不接纳贡献怎么办？

**A**: 
- 先作为独立包发布（`skills-engine`）
- 确保接口设计足够抽象，可以移植到 pi
- 后续可以通过 PR 方式贡献上游
- 即使不接纳，独立包也能正常工作

### Q7: 性能如何？大量 skills 时会不会慢？

**A**: 
- 关键词匹配：O(n) 复杂度，n 为 skills 数量
- 缓存编译结果，避免重复解析
- 嵌入索引（BM25）加速搜索
- 预计 1000 个 skills 下匹配时间 < 100ms

### Q8: 是否支持 Claude Code 的所有 skills 特性？

**A**: 
- Phase 1-2: 支持核心特性（解析、匹配、注入、参数替换、权限）
- Phase 3: 支持高级特性（语义匹配、fork、缓存）
- Phase 4+: 支持 hooks、plugins、skill-creator eval

### Q9: 跨平台兼容性如何？

**A**: 
- 主要测试环境：Linux/WSL/macOS
- Windows 需要额外测试 subprocess 行为
- 建议用 `shlex.quote()` 处理命令参数

### Q10: 有没有类似的开源项目可以参考？

**A**: 
- Claude Code 官方 skills 文档（最佳参考）
- Pi TypeScript 版的 skills 实现（https://github.com/earendil-works/pi）
- LangChain 的 tools 系统（架构参考）
