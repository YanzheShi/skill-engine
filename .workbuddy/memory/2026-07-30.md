## code-builder 大型代码能力研究（只研究，未动代码）

- 研究对象：skills/code-builder（纯 prompt skill，档位 B tool_dispatch 循环，max_turns=30，human_in_loop 计划确认）
- 关键源码：execution/tool_dispatch.py（783 行，6 工具：bash/read_file/write_file/edit_file/search_files/stop）、tool_defs.py、executor.py、runner.py
- 结论：改中小型局部任务可用；对标 Cline 处理大型项目缺 4 块引擎级能力：
  1. **上下文管理**（致命）：messages 只增不减，仅单条截断 5000 字；无摘要压缩/token 预算
  2. **代码库感知**（致命）：search_files 是 rglob 逐行正则、50 条命中上限、无 gitignore 过滤；无 list_files 目录树、无 AST 签名地图
  3. **编辑容错**：edit_file 精确匹配有原子性但无模糊兜底、无 diff 预览
  4. **检查点/任务持久化**：直接落盘无回滚（Cline 是 shadow git）；run() 内存态，max_iter 耗尽即丢弃进度
  5. 执行环境小问题：Executor 默认 10s 超时跑不了 pytest/build；Windows 走 cmd.exe
- 提出三期路线：P1 保命（上下文管理器+代码库地图+执行器超时）→ P2 可靠（模糊编辑+shadow git 检查点+todo 落盘续跑）→ P3 进阶（子代理探索+tree-sitter AST 工具+Plan/Act 双模式）

## 架构通用性判断（用户问"只做 P1/P2 还符合通用 skill 引擎初衷吗"）
- 关键源码事实：TOOL_DISPATCH_TOOLS 在 tool_defs.py:93 硬编码 6 工具（bash/read_file/write_file/edit_file/search_files/stop），全仓库无工具注册/插件机制；models.py 已有 allowed_tools/disallowed_tools（skill 级工具白黑名单）；register_new_skill 支持热注册新 skill
- 结论：P1/P2 通用项（上下文管理/超时/edit 容错/todo 持久化/执行快照）沉引擎核心 → 强化通用性；code 专用项（ast 地图/git 检查点）必须留 skill 层（自带脚本+SKILL.md 指导），绝不能写进 TOOL_DISPATCH_TOOLS，否则引擎被 code 语义绑架
- 后续加其他 skill：现在就能加（register_new_skill），但只能用固定 6 工具；建议补"工具可插拔接口"（skill 在 frontmatter 声明 extra_tools，引擎动态合并 bind_tools），约 +0.5~1 人天；这修正了 P1 工时（原 9.5 不含此项）
- 决策：分层正确则 P1/P2 不破坏通用性；执行快照应抽象为"文件快照/回滚"而非绑定 git
- 用户尚未拍板；可能下一步细化“工具可插拔接口”设计
